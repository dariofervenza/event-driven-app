# 1. Domain Modelling

Ordering & delivery flow for a food-delivery platform: customers order from
restaurants, the order is prepared, handed to a courier, delivered, then rated.
Payment is collected up front and refunded on cancel/refusal.

## Key decisions / assumptions

1. **Cancel window**: a customer can cancel only while the order is still being
   prepared (`Placed`/`Preparing`); not once it is handed to a courier
   (`HandedToCourier`/`Delivered`).
2. **Refusal => refund**: a restaurant refusal always refunds the up-front payment.
3. **Free-delivery threshold**: subtotal >= threshold waives the delivery fee
   (global threshold; could be per-restaurant).
4. **Payment is a precondition**: an order can only be placed once payment is
   collected; no order without payment.
5. **Price snapshot**: order lines capture price at order time.
6. **One-courier invariant**: a courier has at most one active (undelivered) order.
7. **Rating only after `Delivered`.**
8. **Currency**: single currency assumed (`Money` carries it).

## Domain concepts

### Aggregates (have identity)

- **Order** (core aggregate) — `id`, `customer_id`, `restaurant_id`, `courier_id`,
  `lines`, `payment`, `delivery_fee`, `status`, `rating`. Owns its lifecycle.
- **Restaurant** — `id`, `name`, `is_open`, `menu`. Ordering precondition: must be open.
- **Courier** — `id`, `name`, `state` (Available|OnDelivery), `active_order_id`.
- **Customer** — `id`, `name`, `contact`, `address`.

### Value objects (immutable, no identity)

- **Money** — `amount` (Decimal), `currency`.
- **MenuItem** — `id`, `name`, `price` (Money).
- **OrderLine** — `item_id`, `name`, `unit_price` (Money), `quantity`; `total` (computed).
- **Payment** — `amount` (Money), `status` (Paid|Refunded).
- **DeliveryFee** — `amount` (Money), `waived`; computed from subtotal vs threshold.
- **Rating** — `score` (1..5).

## Order lifecycle

```
Placed --> Preparing --> Ready --> HandedToCourier --> Delivered --> (Rated)
  |             |              |              |
  |             +--> Cancelled (customer)    Refused (restaurant -> refund)
```

- Cancellable only while `Preparing`/earlier.
- Refusable any time pre-delivery => refund.
- Terminal: `Delivered`, `Cancelled`, `Refused`.

## Domain events

Direct `AbstractEvent` subclasses (re-exported in `domain/events/__init__.py`):
`OrderPlaced`, `PaymentCollected`, `OrderPreparationStarted`, `OrderReady`,
`CourierAssigned`, `OrderInTransit`, `OrderDelivered`, `OrderCancelled`,
`OrderRefused`, `PaymentRefunded`, `OrderRated`.

## Bounded contexts / subdomains

- **Ordering** (Order + lines + status)
- **Menu** (Restaurant menu + items)
- **Payment** (collect / refund)
- **Delivery** (couriers, assignment, transit status)
- **Rating**

## Numbered implementation plan

### Phase 1 — Value objects (`domain/value_objects/`)

1. `Money(amount, currency)`.
2. `MenuItem(id, name, price)`.
3. `OrderLine(item_id, name, unit_price, quantity)` + computed `total`.
4. `Payment(amount, status)` + `PaymentStatus` enum.
5. `DeliveryFee` + free-delivery rule (waived when subtotal >= threshold).
6. `Rating(score)`.

### Phase 2 — Entities / aggregates

7. `Customer`.
8. `Restaurant` + `Menu`.
9. `Courier`.
10. `Order` (contains `courier_id`).

### Phase 3 — Order lifecycle / invariants

11. `OrderStatus` enum.
12. Transition methods with guards (place / start_preparation / mark_ready /
    assign_courier / mark_delivered / cancel / refuse / rate).
13. Enforce invariants (cancel window, refusal=>refund, one-courier, snapshot).

### Phase 4 — Domain events

14. New direct `AbstractEvent` subclasses.
15. Re-export each in `domain/events/__init__.py`.

### Phase 5 — Commands

    `RefundPayment`, `RateOrder`.

### Phase 6 — Ports
